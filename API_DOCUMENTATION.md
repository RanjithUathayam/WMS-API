## 2. Authentication

### Login flow
`POST /api/login` (see §4.1) returns a JWT `token`. The frontend must store it and send it back on every subsequent request (to the protected mounts above) as a **custom header**:

```
authenticatetoken: <token>
```

(Not `Authorization: Bearer ...` — the middleware reads `req.headers['authenticatetoken']` literally.)

Token is signed with `jwt.sign({ userId, userGroup }, 'CAL-WMS', { expiresIn: '24h' })` — expires in 24 hours.

### Middleware behavior (`authenticateToken.js`)
For every request on a protected mount:
1. Skips auth entirely if `req.url === '/ERPLogin' | '/login' | '/getPickStationData'`.
2. Otherwise requires the `authenticatetoken` header; missing → `401`.
3. Verifies the JWT; invalid/expired → `403 { status: 0, message: 'Forbidden if token is invalid or expired' }`.
4. Loads the user (`models/login/login`) and their group's rights (`models/master/UserGroup`), attaches `req.user` (with `req.user.Rights` = raw rights JSON string) for controllers to use.
5. Runs a **permission check** (`checkPermission`) that matches the first path segment after the router's mount against a big lookup table (`moduleNames`) of `{endpoint, pattern, moduleName}`. The user's rights (JSON array of pattern strings) must contain the matching `pattern`, unless `req.user.UserGroup === 'Admin'`. No match in the table → `202 { status: 0, message: 'Invalid request endpoint' }`. No permission → `202 { status: 0, message: 'You do not have permission to access this page' }`.
6. Logs the request/response to `Api_Log` (or `Customer_api_logs` for a fixed allow-list of ERP-ish endpoints) via `logAPIToDatabase`.

**Frontend implication:** a `202` response is *not* necessarily "success" for this backend — many success paths also return `202` deliberately (see §3). Always check the `status` (or `success`) field in the JSON body, not just the HTTP status code.

## 3. Response Conventions (two co-existing styles)

This backend evolved over time and has **two different response envelope styles** depending on the module. The frontend mapping layer needs to branch on which module it's talking to.

### Style A — "legacy" (`projectController`, `masterController`, `dataController`, `operationController`, `ERPController`, `HHTController`, `transactionController`, `HistoryController`, `configController`)
```jsonc
// success
{ "status": 1, "message": "...", "data": [...] /* + endpoint-specific extra fields like headers, totalCount, remarks */ }
// failure
{ "status": 0, "message": "error text" }
```
HTTP status code is inconsistent — success is often sent as `200`, but a number of success paths intentionally use `202` (e.g. `createEntity`, `PreBinApproveStatus`). Treat `body.status === 1` as the real success signal.

### Style B — "service layer" (`labelPrintController`, `labelReservationController`, `locationController`)
```jsonc
// success
{ "success": true, "message": "...", "data": { ... } }
// failure
{ "success": false, "code": "SOME_ERROR_CODE", "message": "human readable message" }
```
HTTP status code is meaningful here and maps to the error `code` (see each module's error table below). Use `body.success` as the signal, and `body.code` for programmatic handling/i18n on the frontend.

## 4. Endpoints by Module

### 4.1 Auth / Project — mount `/api` (`routes/projectRoutes.js` → `controller/projectController.js`)

No auth header required for these three (not wrapped in `authenticateToken` at all in `app.js`).

#### `POST /api/login`
Request body:
```jsonc
{
  "username": "string",
  "password": "string",
  // optional — only for HHT device login/registration flow:
  "deviceId": "string",
  "deviceModel": "string",
  "deviceOS": "string",
  "deviceOSVersion": "string"
}
```
Behavior notes:
- Validates `username`/`Pwd` against `models/login/login`.
- If `deviceId` is supplied and the device isn't registered yet, it auto-creates a device row and returns **200** with `status: 0` and a message telling the user to contact admin — i.e. this is a "soft fail" wrapped in a 200, so check `status`, not just HTTP code.
- If the device exists but has no `Rights`, or the user's rights lack both `preBinning_list` and `preBinning_creates`, login is rejected (`202`).
- On success, also writes login-session rows (`UserLog`, `LoginHistory`) and returns a session object the frontend must pass back to `/api/logout`.

Success response:
```jsonc
{
  "status": 1,
  "data": { /* full user row incl. Pwd hash-in-plaintext field, UserGroup, rights, ... */ },
  "rights": "<rights string copied onto data too>",
  "token": "<JWT>",
  "DeviceID": "<deviceRefID or ''>",
  "sessionData": {
    "SESSION_ID": "...",
    "SESSION_START": "YYYY-MM-DD hh:mm:ss",
    "SESSION_END": null,
    "STATUS": "RUNNING",
    "logoutID": 123,
    "UserName": "..."
  }
}
```
Failure: `202 { status: 0, message: "Invalid username and password" }` (or the device-related messages above).

#### `POST /api/logout`
Request body — **must be exactly the `sessionData` object returned by login, wrapped as**:
```jsonc
{ "session_id": { "SESSION_ID": "...", "logoutID": 123, ... } }
```
(Note the odd shape: the whole request body *is* treated as `{ session_id: sessionData }` — the controller destructures `req.body` directly as `sessionId` then reads `sessionId.session_id.SESSION_ID`.)
Response: `200 { status: 1, message: 'Logout Successfull' }` or `202 { status: 0, message: 'Invalid sessionId' }`.

#### `POST /api/changePassword`
```jsonc
{ "userId": "...", "oldPassword": "...", "password": "..." }
```
Validation order: old password must match → new must differ from old → non-empty → length 6–20. Response: `200 { status: 1, message: 'Password Changed Successfully' }` or `202 { status: 0, message: "..." }`.

### 4.2 Master Data — mount `/api/master` (`routes/masterRoutes.js` → `controller/masterController.js`)

Generic CRUD over a small whitelist of models keyed by a `:model` URL param. **Only these `:model` values are supported** (anything else throws at `require()` time → the frontend will get a 500-shaped error, not a clean 404):

`MasterPart`, `MasterBin`, `MasterReason`, `UserManagement`, `UserGroup`, `errortable` (maps to `ErrorTable` model), `RightsList` *(list-only — no `primaryFields` entry, so create/update/delete will throw for RightsList)*.

| Method | Path | Notes |
|---|---|---|
| GET | `/api/master/:model` | List, max 500 rows. `MasterPart` supports query filters `ItemCode`, `ItemName`, `ItemGroup` (all `LIKE %value%`). `MasterBin` supports `BinID`, `BinStatus` (`LIKE %value%`). Returns `{status:1, message:"Lists", headers, data}` — `headers` come from a dynamic column-config table (`Table_Header`, keyed by `type = modelName`). |
| GET | `/api/master/:model/:id` | ⚠️ Bug: calls `model.findByPk({entityId, tableHint...})` — passes an object instead of the id value, so this effectively always looks up by the *object*, not `entityId`. Likely broken/returns wrong data; verify before relying on it from the frontend. |
| POST | `/api/master/:model` | Body = model fields. Checks the model's primary/display field (`primaryFields[modelName][1]`) for a pre-existing duplicate before insert. Sets `CreatedBy` from `req.user.UserName`. Returns the **full refreshed list** (not just the created row) in `data`, with HTTP `202` even on success. |
| PUT | `/api/master/:model/:id` | Body = fields to update, matched by `primaryFields[modelName][0]` = `:id`. Stamps `UpdatedDateTime = GETDATE()`. Returns the full refreshed list. |
| DELETE | `/api/master/:model/:id` | **Soft delete** — sets `IsDelete = 1` on the row matched by `Id = :id` (note: hardcoded `Id`, case-sensitive — double check this matches each model's actual column casing). Returns the refreshed (non-deleted) list. |

Fields returned per model (from `modelFieldsMap`) — useful for building frontend grid columns:
- `MasterPart`: id, ItemCode, ItemName, ItemGroup, Category, Description, Color, Size, Style, BinCapacity, Field1-3, Created/Updated/Deleted/Activated (Date+By), isActive, computed `Status` (0/1 from `isDelete`)
- `MasterBin`: AliasBinID, BinID, BinStatus, Created/Updated/Deleted/Activated (Date+By), isActive, computed `Status`
- `MasterReason`: id, ReasonID, ReasonDescription, Created/Updated (Date+By), computed `Status`
- `UserManagement`: id, FullName, UserName, Pwd (⚠️ plaintext), UserGroup
- `UserGroup`: Id, groupname, rights, computed `Status`
- `errortable`: id, EquipmentType, ErrorCode, ErrorDescription, UpdatedDate, computed `Status`
- `RightsList`: id, module, sub_module, lists, creates, modifies, deletes, exports, pattern

### 4.3 Master Export — mount `/api/masterExport` (`routes/masterExport.js`)

### 4.7 Transaction — mount `/api/transaction` (`routes/transactionRoutes.js` → `controller/transactionController.js`)

#### `GET /api/transaction/inventory`
Query params: `type` (`'Inventory'` | `'TotalInventory'` | `'TotalInventoryAisle'` — anything else returns empty query results), plus optional filters `itemCode`, `itemname`, `itemgroup`, `binid`, `craneid`, `sortKey`, `sortFormat`, `exportFormat`.
- `type=Inventory`: per-pallet/location rows, capped at 500 unless exporting.
- `type=TotalInventory`: aggregated per item/aisle/shuttle totals (excludes bins with an open pallet request).
- `type=TotalInventoryAisle`: per-item totals broken out by 4 fixed aisles (`AisleNo` 1–4).
- Response: `{ status, message, header, data, totalRecord }` (JSON) or a file stream if `exportFormat` set.
- ⚠️ **SQL built via string concatenation** of the query params directly into the SQL text (not parameterized) for this endpoint — treat all filter inputs as needing strict frontend-side validation/allow-listing, and flag this to the backend team as a SQL-injection risk if these query params ever accept free-text user input.

### 4.12 Label Reservation & Printing — mount `/api/label` (`routes/labelReservationRoutes.js` → `controller/labelReservationController.js` → `service/labelReservationService.js`)

Uses **Style B** envelopes.

#### `POST /api/label/reserveLabelNumbers`
```jsonc
{ "labelCount": 10 }   // integer, 1–1000
```
Reserves N sequential Label Numbers (format `YYYYMMDD` + 4-digit running number) without needing any item/template data yet.
```jsonc
{ "success": true, "labelCount": 10, "labels": [ { "labelNumber": "202608290001", "qrValue": "202608290001" }, ... ] }
```
Error: `VALIDATION_ERROR` (400) if `labelCount` missing/non-integer/≤0/>1000.

#### `POST /api/label/print`
Two accepted body shapes (backend supports both):
```jsonc
// Shape 1 — original
{ "labelNumbers": ["202608290001", "202608290002"], "copies": 2, "printerName": "...", "density": 10, "speed": 2, "gapMm": 3, "offsetMm": 0, "labelWidthMm": 90, "labelHeightMm": 44, "mfgDate": "2026-08-29", "dpi": 203, "rotation": 0 }
// Shape 2 — per-label copies override
{ "labels": [ { "labelNumber": "202608290001", "copies": 1 }, { "labelNumber": "202608290002", "copies": 3 } ], "printerName": "..." }
```
All settings fields (`printerName`, `density`, `speed`, `gapMm`, `offsetMm`, `labelWidthMm`, `labelHeightMm`, `dpi`, `rotation`) are **optional** — the backend fills sane defaults per-printer from its capability profile. `rotation` must be one of `0, 90, 180, 270` if supplied.
Only Label Numbers with status `Reserved` or `Failed` can be printed (re-printing a `Failed` one is how retries work — same request, no new number). Verifies each labelNumber was actually reserved before printing.
```jsonc
{
  "success": true, "message": "Print job completed successfully",
  "data": {
    "printerName": "...", "density": 10, "speed": 2, "gapMm": 3, "offsetMm": 0,
    "labelWidthMm": 90, "labelHeightMm": 44, "mfgDate": null, "dpi": 203, "rotation": 0,
    "printableXMm": 18, "printableWidthMm": 63,
    "labelCount": 2, "totalPhysicalPrints": 3,
    "labels": [ { "labelNumber": "...", "qrValue": "...", "status": "Printed" } ],
    "command": "<raw TSPL command string sent to printer>"
  }
}
```
Error codes → HTTP: `VALIDATION_ERROR` (400), `LABEL_NUMBERS_NOT_FOUND` (400), `LABEL_NOT_PRINTABLE` (409), `PRINTER_NOT_CONFIGURED` (404), `PRINTER_NOT_FOUND` (404), `PRINTER_OFFLINE` (409), `PRINTER_DETECTION_FAILED` (503), `PRINT_COMMAND_GENERATION_FAILED` (500), `PRINTABLE_AREA_EXCEEDED` (400 — content wouldn't fit the label), `PRINT_FAILED` (502).

#### `GET /api/label/printers`
Returns the (possibly cached) list of detected OS printers: `{ success: true, printers: [ { name, isDefault, status } ] }`.

#### `POST /api/label/printers/detect`
Same as above but forces a fresh OS query (bypasses cache).

```jsonc
{ "locationId": 1, "warehouseCode": "WH1", "rowCode": "A1", "positionNo": 5, "locationCode": "WH1-A1-005", "status": "AVAILABLE", "currentPalletId": null, "occupiedBy": null, "occupiedAt": null, "createdBy": "...", "createdAt": "...", "updatedBy": null, "updatedAt": null }
```

### 4.14 Pallet Mapping — mount `/api/pallet-mapping` (`routes/palletMappingRoutes.js` → `controller/palletMappingController.js` → `service/palletMappingService.js`)

Uses **Style B** envelopes. Maps completed Pre-Binning boxes onto a pallet. A `PalletID` is **single-use for its whole lifetime**: once its mapping is `COMPLETED` it can never be reopened or reused, even if it later becomes physically available again — a re-scan of a completed PalletID is rejected, not resumed.

| Method | Path | Body/Params | Notes |
|---|---|---|---|
| POST | `/api/pallet-mapping/pallet/validate` | `{ palletId }` | Scans/validates a `PalletID`: resumes its existing `OPEN` mapping if one exists, otherwise opens a new one. Rejects with `PALLET_ALREADY_COMPLETED` if that `PalletID` was already completed. |
| GET | `/api/pallet-mapping/pallet/:palletId` | — | Read-only status lookup — latest mapping (any status) for the PalletID, with its mapped boxes. `PALLET_NOT_FOUND` (404) if the PalletID has no mapping at all. |
| POST | `/api/pallet-mapping/box` | `{ palletId, boxNumber }` | Maps one eligible box onto the pallet's `OPEN` mapping. A box is only eligible once its Pre-Binning workflow is `COMPLETED`, and each box can be mapped to exactly one pallet ever. |
| POST | `/api/pallet-mapping/complete` | `{ palletId }` | Marks the pallet's `OPEN` mapping `COMPLETED` — permanent, per the single-use rule above. Requires at least one mapped box (`PALLET_HAS_NO_BOXES` if zero). |

`toMappingDto` shape returned by all four endpoints (`data`):
```jsonc
{
  "palletMappingId": 1,
  "palletId": "PLT-0001",
  "totalBoxCount": 2,
  "status": "OPEN", // or "COMPLETED"
  "createdBy": "...",
  "createdAt": "...",
  "completedBy": null,
  "completedAt": null,
  "boxes": [
    {
      "palletMappingBoxId": 1,
      "palletMappingId": 1,
      "palletId": "PLT-0001",
      "boxNumber": "BOX-0001",
      "warehouseCode": "WH1",
      "itemGroup": "...",
      "boxTotalQty": 24,
      "mappedBy": "...",
      "mappedAt": "..."
    }
  ]
}
```

Error codes → HTTP status: `MISSING_FIELDS` (400), `PALLET_NOT_FOUND` (404), `PALLET_NOT_OPEN` (409 — no `OPEN` mapping exists yet for that PalletID; validate it first), `PALLET_ALREADY_COMPLETED` (409), `PALLET_HAS_NO_BOXES` (409), `BOX_NOT_FOUND` (404), `BOX_NOT_ELIGIBLE` (409 — box hasn't completed Pre-Binning), `BOX_ALREADY_MAPPED` (409).

Concurrency: validate/add-box/complete all take a row lock (`UPDLOCK, ROWLOCK, HOLDLOCK`) on the pallet mapping (and, for add-box, on the Pre-Binning box row too) inside a DB transaction, so concurrent scans of the same PalletID or BoxNumber serialize correctly instead of racing.

> ⚠️ **Permission table gotcha** (see `authenticateToken.js`'s `moduleNames`, verified against the routes above): `checkPermission()` keys off only the **first path segment** after the mount, regardless of which router the request actually came through.
> - `POST /pallet/validate` and `GET /pallet/:palletId` both key off `/pallet` → require the `palletMapping_list` rights pattern.
> - `POST /complete` keys off `/complete` → requires `palletMapping_creates`.
> - `POST /box` keys off `/box`, but there is **no** `/box` entry registered for Pallet Mapping — it falls through to the pre-existing Pre-Binning entry and is gated by `preBinning_creates` instead of a Pallet-Mapping-specific permission. When setting up a role's rights for this screen, grant `preBinning_creates` (not a `palletMapping_*` variant) for the "add box" action, or box-mapping calls will 202 with "You do not have permission" even after granting every `palletMapping_*` right.

### 4.15 Location Mapping — mount `/api/location-mapping` (`routes/locationMappingRoutes.js` → `controller/locationMappingController.js` → `service/locationMappingService.js`)

Uses **Style B** envelopes. Assigns an already-`COMPLETED` Pallet Mapping (§4.14) to a physical warehouse location, and — as a side effect of that same call — populates `T_INVENTORY` with the pallet's contents at that location.

| Method | Path | Body/Params | Notes |
|---|---|---|---|
| POST | `/api/location-mapping/map` | `{ palletId, locationCode, whsCode?, rowCode? }` | Scans a pallet onto a location. `whsCode`/`rowCode` are optional cross-checks against the location resolved from `locationCode` — pass them if the scan UI has them, to catch a wrong/stale barcode read. |

Processing order (one DB transaction, both target rows locked for the duration):
1. Locks the location by `locationCode`. 404 `LOCATION_NOT_FOUND` if it doesn't exist; 400 `LOCATION_MISMATCH` if a supplied `whsCode`/`rowCode` doesn't match that location's actual warehouse/row; 409 `LOCATION_NOT_AVAILABLE` if its `Status` isn't `AVAILABLE` (i.e. already `OCCUPIED`/`BLOCKED`/`INACTIVE`).
2. Locks the pallet's latest mapping by `palletId` (same lookup Pallet Mapping's `validate`/`GET` use). 404 `PALLET_NOT_FOUND` if it has no mapping at all; 409 `PALLET_NOT_COMPLETED` if that mapping exists but isn't `COMPLETED` yet — **the pallet's Pallet Mapping validate → box → complete flow (§4.14) must finish first**, mapping a still-`OPEN` pallet is rejected.
3. Inserts an `ACTIVE` audit row into `T_LOCATION_MAPPING` and flips the location to `Status: 'OCCUPIED'` (`CurrentPalletMappingID`/`CurrentPalletID`/`OccupiedBy`/`OccupiedAt` set). A DB-level unique-filtered-index backstop (one `ACTIVE` row per pallet, one per location) turns a race into 409 `PALLET_ALREADY_MAPPED` or `LOCATION_ALREADY_OCCUPIED` instead of double-booking.
4. **Inventory side effect**: reads the item/quantity breakdown for every box mapped to that pallet (joining `T_PALLET_MAPPING_BOX` → `T_PREBIN_BOX` → `T_PREBIN_ITEM`, grouped by box + item) and upserts one `T_INVENTORY` row per (location, pallet mapping, box, item) via a `MERGE` — first successful mapping to a location is what actually creates the pallet's inventory records; re-mapping the same pallet/box/item combination updates quantity in place rather than duplicating rows.

Response `data` (`toLocationMappingDto`):
```jsonc
{
  "locationMappingId": 1,
  "locationId": 5,
  "locationCode": "THNMOV-A-001",
  "warehouseCode": "THNMOV",
  "rowCode": "A",
  "positionNo": 1,
  "palletMappingId": 1,
  "palletId": "PLT-0001",
  "action": "MAPPED",
  "status": "ACTIVE",
  "mappedBy": "...",
  "mappedAt": "..."
}
```

Error codes → HTTP status: `MISSING_FIELDS` (400), `LOCATION_NOT_FOUND` (404), `LOCATION_MISMATCH` (400), `LOCATION_NOT_AVAILABLE` (409), `LOCATION_ALREADY_OCCUPIED` (409), `PALLET_NOT_FOUND` (404), `PALLET_NOT_COMPLETED` (409), `PALLET_ALREADY_MAPPED` (409).

> ⚠️ **Permission table note**: `POST /map` keys off the `/map` first path segment → requires the `locationMapping_creates` rights pattern (per `authenticateToken.js`'s `moduleNames`). Unlike Pallet Mapping's `/box`, this segment isn't shared with any other module, so no extra permission gotcha here.

## 5. Known Issues / Gotchas for Frontend Integration

1. **Two response envelope conventions** (§3) — build one adapter per module family, not a single generic response parser.
2. **`202` does not mean "client error"** in this API's convention for many legacy endpoints — always branch on the JSON `status`/`success` field.
3. **`GET /api/master/:model/:id`** appears to pass the wrong value into `findByPk` (an object instead of the id) — verify actual behavior against a running instance before wiring up an "edit single record" screen; it may not filter correctly.
4. **`getDeveiceDetails`** (HHT) is a real typo in the route path — the frontend must call that exact misspelled path.
5. **`/api/data/*` and `/api/masterExport/*`** are not authenticated at all — don't assume a missing/expired token will block them.
6. Several endpoints build SQL by string-concatenating request input (`transactionController.inventoryList`, `configController.getPickStationData`) — treat those query/body parameters as sensitive and validate format client-side even though this is ultimately a backend fix needed.
7. `authenticateToken.js`'s permission table references many endpoints/routers that don't exist in this codebase (see the warning at the top of this document) — don't use that file as a source of truth for what's callable; use this document / the actual `routes/*.js` files instead.
8. Master CRUD (`/api/master/:model`) only supports the 6–7 whitelisted model names listed in §4.2 — any other value will error.
9. **Pallet Mapping's "add box" permission** (§4.14) is gated by `preBinning_creates`, not a `palletMapping_*` pattern, because `checkPermission()` resolves permissions by first path segment (`/box`) only and that segment is already claimed by the Pre-Binning module — grant `preBinning_creates` to any role that needs to map boxes onto pallets.
10. A `PalletID` is single-use for its entire lifetime in Pallet Mapping (§4.14) — once `COMPLETED`, re-validating the same PalletID always fails with `PALLET_ALREADY_COMPLETED`, it never reopens.
11. **`POST /api/location-mapping/map` (§4.15) is where `T_INVENTORY` rows actually get created** — a pallet's boxes/items exist in Pre-Binning/Pallet Mapping tables beforehand, but nothing appears in Inventory until it's mapped to a location. If a frontend screen expects to see a completed pallet's stock in an inventory list before it's been placed in a bin, that data won't exist yet.
12. Location Mapping (§4.15) can only ever map a `COMPLETED` Pallet Mapping — there is currently no "unmap"/"relocate" endpoint (the schema reserves `Action = 'UNMAPPED'|'MOVED'` and `Status = 'SUPERSEDED'` for this, per `sql/Location_Schema.sql`'s comments, but no route/service implements it yet). Once mapped, a pallet/location pair can't be changed through the API.
